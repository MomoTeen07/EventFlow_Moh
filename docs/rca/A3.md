# RCA A3 (B4): Code promo expiré accepté

## Symptôme observé

Le code promo `EXPIRED` est accepté lors d'une commande alors que sa date de validité est dépassée. Le test UI n'observe pas le message attendu et l'utilisateur arrive sur l'écran de paiement.

## Impact (pour l'utilisateur, pour l'entreprise)

- **Utilisateur :** l'application accepte un code qui devrait être refusé.
- **Entreprise :** une remise de 15 % peut être accordée après expiration, avec une perte de revenu et un contournement des règles promotionnelles.

## Preuves (commandes, captures de la trace, ligne de code)

- Le test UI `test_expired_promo_code_shows_error` échoue de façon identique 3 fois sur 3 à la ligne 52 de [test_booking_ui.py](../../qa/tests/ui/playwright/test_booking_ui.py); il attend `Promo code expired`.
- Le test saisit `EXPIRED` puis clique sur « Continuer vers le paiement » aux lignes 50–51. La trace Playwright locale, non jointe car `qa/reports/` est ignoré par Git, confirme la saisie et `POST /api/orders` en HTTP 201. La commande UI est `pending`, totalise 2 975 centimes et mène à l'écran de paiement. La trace ne contient pas d'événement console de niveau erreur.
- Le test API [test_booking_rules.py](../../qa/tests/api/test_booking_rules.py:23) échoue pour `[EXPIRED]` : il attend 400 à la ligne 26 et reçoit 201. La réponse pour deux billets totalise 5 950 centimes.
- [codes_promo.json](../../qa/data/codes_promo.json:4) spécifie HTTP 400 pour `EXPIRED`.
- La requête SQL exécutée indique une expiration au `2026-11-11 12:21:02.399541` et `expires_at < NOW() = true`.
- `GET /api/config` a retourné `seed_bugs: true` pendant l'investigation.
- [orders.py](../../backend/app/routers/orders.py:34) contient le contrôle d'expiration conditionnel.
- Lors de l'enquête B4, l'étape UI portait `continue-on-error: true`, ce qui pouvait masquer son échec. Cette anomalie de détection a été corrigée dans A4; voir [A4.md](./A4.md).

## Cause racine

Dans `_validate_promo()`, le refus d'une date d'expiration passée est désactivé lorsque `settings.seed_bugs` est vrai :

```python
if promo.expires_at and promo.expires_at < datetime.utcnow() and not settings.seed_bugs:
```

Le contrôle ne lève donc pas HTTP 400 en mode bugs; la création de commande se poursuit et applique la remise. Lors de l'enquête, la CI présentait en plus un défaut de détection distinct, désormais corrigé localement dans A4.

## Actions correctives

- **Produit :** appliquer la règle d'expiration indépendamment du mode de démonstration lorsque le comportement attendu est testé.
- **Processus de test :** conserver les tests API/UI du cas expiré et faire échouer le job CI quand les tests UI échouent, tout en permettant aux étapes de diagnostic suivantes de s'exécuter; l'ajustement CI correspondant est fait dans A4.

## Comment vérifier que c'est corrigé

1. Rejouer `pytest tests/api/test_booking_rules.py::test_rm4_promo_codes[EXPIRED] -q` depuis `qa`.
2. Rejouer `pytest tests/ui/playwright/test_booking_ui.py::test_expired_promo_code_shows_error -q` depuis `qa`.
3. Vérifier que l'API retourne 400, que l'interface affiche `Promo code expired` et qu'aucune commande n'est créée.
4. Vérifier sur une exécution GitHub Actions qu'un échec UI rend le job CI rouge; ce comportement n'a pas encore été vérifié sur le serveur distant.

## Rapport d'anomalie B4 (prêt à publier)

- **Titre :** Le code promo EXPIRED est accepté et ouvre le paiement malgré son expiration.
- **Environnement :** branche `mission-lundi`, backend Docker en mode `SEED_BUGS=true`, navigateur Chromium.
- **Étapes :**
  1. Se connecter avec le compte QA.
  2. Ouvrir un événement et ajouter un billet « Plein tarif ».
  3. Saisir `EXPIRED`.
  4. Cliquer sur « Continuer vers le paiement ».
- **Résultat attendu :** HTTP 400 et message UI `Promo code expired`.
- **Résultat obtenu :** HTTP 201, commande en attente avec total de 2 975 centimes, puis écran de paiement.
- **Fréquence :** échec UI identique 3/3; cas API en échec lors de l'exécution ciblée.
- **Gravité :** élevée, car un code expiré donne encore une remise et le contrôle de validité est contourné.
- **Preuves :** tests UI/API, date SQL ci-dessus, trace Playwright et condition de [orders.py:34](../../backend/app/routers/orders.py:34).
