# A4 — Fiabilisation des tests UI et du pipeline

## Symptôme observé

Avant le travail A4, les deux tests du parcours de paiement avaient `@pytest.mark.flaky(reruns=3)`. Le premier contenait aussi `time.sleep(2)` avec un commentaire signalant un problème intermittent du bouton de paiement.

Les étapes Playwright et Selenium du workflow CI avaient `continue-on-error: true`; leurs échecs pouvaient être tolérés par le job.

## Impact

- **Utilisateur :** un défaut du parcours de paiement pouvait ne pas être détecté de façon fiable.
- **Équipe :** les relances et attentes fixes réduisaient la valeur diagnostique des tests; la CI pouvait ne pas signaler certains échecs UI.

## Preuves et changements réalisés

- Dans [test_checkout_e2e.py](../../qa/tests/ui/playwright/test_checkout_e2e.py), les deux marqueurs de relance et l'attente `time.sleep(2)` ont été retirés; l'import `time` inutilisé a également été supprimé.
- Dans [ci.yml](../../.github/workflows/ci.yml), les deux `continue-on-error: true` ont été remplacés par `if: success() || failure()` sur les étapes Playwright et Selenium. Ces étapes s'exécutent donc après un échec précédent, mais leur propre échec n'est plus neutralisé.
- Le backend a été relancé avec `SEED_BUGS=false`; `GET /api/config` a confirmé cette valeur.
- La commande `pytest tests/ui/playwright` a terminé avec **20 passed**. Un avertissement de dépréciation lié à `datetime.utcnow()` dans une fabrique de test est resté; il n'a pas fait échouer la suite.

## Cause racine

Les relances automatiques et l'attente fixe masquaient le manque de synchronisation explicite dans le test. Le workflow neutralisait en plus les échecs des deux suites UI avec `continue-on-error`.

## Actions correctives

- **Tests :** supprimer les relances et le délai fixe; laisser les assertions de l'interface révéler un échec réel.
- **CI :** poursuivre l'exécution des tests UI après un échec antérieur, sans transformer un échec UI en succès du job.

## Comment vérifier

1. Confirmer l'absence de `@pytest.mark.flaky`, `time.sleep` et de l'import `time` dans `test_checkout_e2e.py`.
2. Confirmer que les deux étapes CI utilisent `if: success() || failure()` et n'ont plus `continue-on-error`.
3. En mode normal, rejouer `pytest tests/ui/playwright` depuis `qa`; résultat observé ici : **20 passed**.
4. Vérifier sur GitHub Actions qu'un échec simulé d'une étape API n'empêche pas les étapes UI de s'exécuter, et qu'un échec UI rend le job rouge. Cette vérification distante reste à faire.

## Rapport A4

- **Titre :** Les tests UI de paiement et le pipeline pouvaient masquer des échecs.
- **Environnement :** branche `mission-lundi`, Docker en mode normal, Playwright/Chromium; workflow GitHub Actions.
- **Étapes :** consulter les anciens marqueurs et l'attente du parcours de paiement; examiner les conditions des étapes UI et Selenium dans le workflow.
- **Résultat attendu :** les tests exposent les échecs sans relance ni attente arbitraire; le job échoue sur un échec UI.
- **Résultat obtenu avant A4 :** les tests avaient trois relances et un délai fixe; la CI tolérerait les échecs UI/Selenium.
- **Fréquence :** non mesurée avant correction; après correction, la suite UI a réussi une fois (20 tests).
- **Gravité :** moyenne à élevée, car un défaut UI pouvait être masqué par le pipeline.
- **Preuves :** fichiers test et workflow référencés ci-dessus; résultat pytest local.
