# RCA A1 (B1) — Survente de billets VIP

## Symptôme observé

Le test `test_rm1_cannot_order_more_than_available_stock` a constaté une disponibilité VIP de 3 billets, puis une réponse HTTP 201 pour une demande de 4 billets. La commande retournée contient un article de quantité 4 (catégorie ID 234), alors que le test attend HTTP 409.

Après cette réservation, la requête SQL fournie indique pour la catégorie VIP d’ID 234 un quota de 3 et un total de 4 billets réservés dans les commandes `pending` ou `paid`.

## Impact pour l'utilisateur et pour l'entreprise

- **Utilisateur :** une commande est confirmée alors que le stock disponible ne permet pas de garantir tous les billets. L’organisateur peut devoir annuler ou rembourser la réservation.
- **Entreprise :** l’inventaire peut être sur-réservé, entraînant des coûts de traitement, des remboursements et une perte de confiance.

## Cause racine

Dans `create_order()`, le contrôle RM1 est écrit ainsi :

```python
if item.quantity > category_available(db, category) and not settings.seed_bugs:
```

Quand `SEED_BUGS=true` configure `settings.seed_bugs` à `True`, la clause `and not settings.seed_bugs` est fausse. Le contrôle ne lève donc pas l’exception HTTP 409, même si la quantité demandée dépasse le stock disponible. La commande et son article sont ensuite ajoutés et enregistrés.

`category_available()` calcule le quota moins le nombre de billets déjà réservés selon `category_sold()`, avec un plancher à zéro. En mode bugs, `category_sold()` compte aussi les commandes en attente expirées : c’est le comportement B5, distinct de la désactivation du contrôle RM1 à l’origine du B1 observé.

Le contrôle est également une lecture suivie plus tard d’une écriture. Les résultats décrits établissent le contournement dû à `seed_bugs`; ils ne prouvent pas qu’une concurrence entre requêtes a contribué à cet incident. Une protection contre les réservations simultanées nécessiterait une analyse et une stratégie de cohérence transactionnelle distinctes.

## Actions correctives proposées

- **Produit :** rendre le refus RM1 effectif même lorsque `seed_bugs` est activé; examiner séparément la protection contre les réservations simultanées.
- **Processus de test :** conserver le cas d'API qui attend HTTP 409 et l'exécuter dans le mode où B1 est actif; ne pas confondre B1 avec B5.

## Comment vérifier que le problème est corrigé

1. Avec les données de test réinitialisées, confirmer que la catégorie VIP a 3 places disponibles.
2. Rejouer `pytest tests/api/test_booking_rules.py::test_rm1_cannot_order_more_than_available_stock` dans la configuration de test qui active `SEED_BUGS=true`.
3. Vérifier que la requête de 4 billets retourne HTTP 409 et qu’aucune commande ni ligne `order_items` correspondante n’est créée.
4. Relancer `pytest tests/api/test_booking_rules.py` pour vérifier les règles de réservation voisines.
5. Si une protection contre les courses concurrentes est ajoutée, exécuter en plus un test de concurrence ciblé et vérifier que le total des réservations ne dépasse jamais le quota.
